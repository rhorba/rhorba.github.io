10 signes que votre application Java EE doit être modernisée

Chaque point se vérifie en moins de dix minutes, sur votre propre système, sans faire venir personne.

Cochez ce qui est vrai chez vous. Ce qui compte n'est pas le total, mais lesquels : certains signes coûtent un peu tous les mois, d'autres bloquent tout le reste tant qu'ils ne sont pas traités.

  1. Votre serveur d'applications n'est plus supporté

    JBoss AS 7, WildFly antérieur à la 26, Tomcat 8 : plus de correctifs, y compris de sécurité. Vos audits de conformité le verront avant vous.

    À vérifier : la version exacte du serveur en production, comparée à sa date de fin de support éditeur.

  2. Vous êtes bloqué sur Java 8 ou Java 11

    Ce n'est presque jamais Java qui bloque, mais deux ou trois dépendances abandonnées qui n'existent pas en version récente. Tant qu'elles ne sont pas remplacées, aucune montée de version n'est possible.

    À vérifier : lancez la build avec un JDK récent et notez les trois premières erreurs. Ce sont elles, le vrai sujet.

  3. Le passage de javax.* à jakarta.* n'a pas été fait

    C'est le mur. Spring Boot 3, Jakarta EE 10 et les versions récentes de la plupart des bibliothèques sont tous derrière. Tant qu'il n'est pas franchi, chaque autre modernisation est repoussée.

    À vérifier : cherchez import javax.persistence ou javax.servlet dans le code.

  4. Un déploiement n'est pas reproductible

    S'il faut une personne précise, un fichier de configuration qui n'est pas dans le dépôt et une heure creuse, ce n'est pas un déploiement : c'est un rituel. C'est aussi la première cause d'incidents en production.

    À vérifier : un développeur arrivé la semaine dernière peut-il déployer en préproduction seul, en une commande ?

  5. La base de données n'a pas de migrations versionnées

    Pas de Flyway ni de Liquibase, des scripts SQL échangés par mail ou appliqués à la main : personne ne peut dire avec certitude si la préproduction et la production ont le même schéma.

    À vérifier : existe-t-il une table d'historique des migrations ? Sinon, la réponse est non.

  6. Personne ne connaît la couverture de tests

    Une couverture faible est un problème gérable. Une couverture inconnue signifie que chaque modification est un pari, et c'est ce qui rend la modernisation effrayante — pas le code lui-même.

    À vérifier : la build produit-elle un rapport de couverture ? Sa seule absence est déjà la réponse.

  7. La logique métier vit dans les pages JSF

    Des backing beans de plusieurs milliers de lignes où les règles métier, l'accès aux données et l'affichage sont mélangés. Conséquence directe : impossible d'exposer une API, d'ajouter un canal mobile ou de tester quoi que ce soit isolément.

    À vérifier : ouvrez les trois plus gros fichiers *Bean.java. Contiennent-ils des règles de gestion ?

  8. Les processus BPMN n'existent que dans le moteur

    Les workflows Activiti ou jBPM tournent, mais leur définition n'est documentée nulle part et le déploiement d'une nouvelle version fait peur. Ce sont pourtant vos processus métier les plus critiques.

    À vérifier : quelqu'un peut-il expliquer, schéma à l'appui, ce que fait le processus le plus utilisé ?

  9. Une seule personne peut intervenir sur le système

    Le risque n'est pas qu'elle parte : c'est qu'elle prenne des vacances au mauvais moment. Tant que la connaissance n'est pas sortie d'une seule tête, aucun chiffrage n'est fiable.

    À vérifier : combien de personnes ont livré un correctif en production ces six derniers mois ?

  10. Chaque évolution métier coûte plus cher que la précédente

    C'est le signe le plus coûteux, et le plus facile à ignorer parce qu'il progresse lentement. Il finit par se payer en délais commerciaux, pas seulement en jours de développement.

    À vérifier : comparez le temps passé sur les trois dernières demandes de complexité comparable, à un an d'écart.

Ce que votre total veut dire

0 – 2
Votre système vieillit normalement. Planifiez les montées de version, ne changez rien d'autre.
3 – 5
Le coût est déjà là, réparti sur chaque demande d'évolution. C'est le moment le moins cher pour agir : vous choisissez encore le calendrier.
6 et plus
La modernisation n'est plus une décision, c'est une échéance. Commencez par les points 3, 4 et 6 — ils débloquent tous les autres.
